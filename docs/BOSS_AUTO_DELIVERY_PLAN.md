# BOSS 自动沟通与简历投递实施计划

日期：2026-10-01。依据：当前仓库实现、`IMPLEMENTATION_REVIEW.md` 中的登录页面观察和已授权的单岗位验证。本计划中的页面状态仅代表当次账号观察；上线门槛以新的现场证据为准。

> 历史计划说明：下方“当前基线”记录制定计划时的状态，已不代表 2026-10-02 的交付能力。当前 BOSS／猎聘任务以扩展中的一次按钮点击为完成边界，平台会话与简历由人工确认；工作台只读，未知结果在扩展登记。使用方式与验收边界见 `README.md`、`EXTENSION_USAGE.md`。

## 1. 交付目标与边界

目标是用户在 Chrome 扩展中启动一个明确授权的任务后，系统从用户指定的 [北京 AI产品经理搜索页](https://www.zhipin.com/web/geek/jobs?query=AI%E4%BA%A7%E5%93%81%E7%BB%8F%E7%90%86&city=101010100&industry=&position=) 进入，按左侧列表顺序处理实际同时与 AI、产品工作相关的岗位。每个岗位依次完成：列表与详情身份核对、相关性判断、去重、必要时点击一次“立即沟通”、核验消息结果、在平台允许且已绑定正确简历时发送站内简历、核验附件结果、回到列表继续下一岗位。预算用来分批执行，不作为岗位筛选条件；不额外搜索其他关键词，也不按薪资、职级筛选。该搜索入口可能遗漏搜索结果之外的相关岗位，不能宣称全站覆盖。

“自动投递”在界面和账本中拆成两个独立结果：`CONTACT_INITIATED` 表示本轮沟通已获得新消息或平台明确回执；`SENT` 表示本轮在正确会话中发送了绑定简历且有新的附件证据。仅打开聊天、看到旧消息或点击按钮，都不等于上述结果。BOSS 若要求双方回复后才能使用“发简历”，此岗位进入 `WAITING_PEER`，保留后续处理资格，不能宣称当场投递完成。

首版限定：一个 BOSS 账号、一个前台 Chrome 扩展执行者、站内已有简历。招聘方回复、交换联系方式、付费、验证码、登录验证和平台明确限制交由用户处理。桌面操作仅在真实页面证据证明扩展无法完成某个允许动作时补充；Jev 或其他模型只判断模糊岗位语义或页面状态，不决定授权、发送成功或任意执行动作。

## 2. 当前基线

| 模块 | 当前事实 | 距离真实自动投递的缺口 |
| --- | --- | --- |
| 岗位发现 | BOSS 登录页已验证左卡片、右详情共用岗位 ID，整页滚动可续载；扩展能只读扫描列表 | 用户指定搜索页的真实扫描、聊天后的列表恢复及动态列表锚点丢失时的有界重扫仍需验证 |
| 岗位判断 | 规则已区分 `INCLUDE / EXCLUDE / NEEDS_REVIEW`；不限制精确“AI 产品经理”名称 | 模糊语义需抽样复核，可选模型需脱敏评估；不能以模型分数淘汰明确相关岗位 |
| 本地执行 | 扩展、FastAPI、PostgreSQL、工作台和 fixture 发送闭环存在；意图先入账、账号互斥、`UNKNOWN` 门禁存在 | fixture 的成功不能解锁 BOSS；当前真实 BOSS `send_ready=false` 且服务端拒绝外部发送 |
| 真实开聊 | 用户授权的单岗位“立即沟通”已点击一次，对应会话可见己方已送达消息 | 点击前未保存消息 ID 基线，无法证明是本次新消息，结果仍为 `UNKNOWN`；不能自动重试 |
| 真实简历 | 已在消息页看见“发简历”入口；当次会话提示双方回复后可用 | 会话与岗位绑定、已有简历身份/版本、可用态、多步选择/确认、发送后证据均未验证；发送次数为零 |
| 使用界面 | 扩展可只读扫描，未决动作在工作台持续可见 | 用户还无法启动真实 BOSS 自动发送；需要展示每种能力、等待和人工接管的真实原因 |

制定本计划时，可交付能力仍是**真实 BOSS 只读发现与判断**。指定 URL 的真实页面当时已有 15 张卡片，更新后的扩展完成 3 岗位只读批次，外部动作 0；真实消息页可记录匿名名片和可见消息的只读基线，但没有平台稳定会话 ID，也尚未绑定岗位/发送命令。该历史 `UNKNOWN` 不因计划推进而改写为成功或失败；现应先只读核对证据，再由用户在扩展中登记结论，绝不自动重试。

## 3. 完整执行契约

1. **启动**：扩展确认当前登录账号、用户指定的北京搜索 URL、站内简历策略和本轮预算，冻结任务范围与控制权。只有用户明确启动的任务能产生外部效果；页面未准备好时给出可执行原因。
2. **发现与选择**：顺序处理可见岗位，稳定岗位 ID 去重；左卡片与右详情的 ID、标题、工作地一致后形成 `selection_epoch`。只包含 AI 与产品双重相关且工作地为北京的明确岗位；矛盾信息进入 `NEEDS_REVIEW`。
3. **开聊前预检**：确认没有账号级未决动作、没有该岗位或共享会话的历史成功、招聘对象和按钮仍正确；定位目标会话的可验证身份并记录点击前消息 ID 集或可用的平台序号。先持久化 CONTACT 意图与页面快照，再给一次性点击许可。
4. **点击与核验**：只点击一次“立即沟通”及已验证的原生必要确认。跨职位页和消息页追踪同一动作；只有正确会话出现比基线新增、属于己方、状态明确的消息或等价平台回执时记录本次 `CONTACT_INITIATED`。单纯跳转、分钟级时间、旧消息和本机时间都不算。证据不足为 `UNKNOWN`，暂停账号外部动作。
5. **简历条件分支**：在已绑定的正确会话读取“发简历”状态。被平台禁用且提示需双方回复时记 `WAITING_PEER`；没有入口时区分 `NOT_CHECKED` 与 `UNAVAILABLE`；出现验证码、异常交互或多份简历无法选择时接管。
6. **简历发送与核验**：入口可用时核对用户预先绑定的站内简历身份/版本与目标会话，先持久化 RESUME_SEND 意图，然后执行真实已验证的选择/确认步骤。仅在出现比发送前基线新增的附件消息或明确回执，且可关联到会话与绑定简历时记 `SENT`；否则 `UNKNOWN`。同一会话同一附件不盲目重复发送。
7. **恢复与续批**：回到原列表，重读账号、页面、岗位锚点和未决动作。按稳定 ID 跳过已处理岗位；锚点失效时有界重扫。连续两次完整等待未见新 ID 时结束本轮为 `LIST_NO_PROGRESS`，不宣称全站穷尽。达到本轮预算时保存未处理队列供下次继续。
8. **控制权**：用户暂停、接管、页面改变、扩展重启、锁屏或连接失效时撤销新动作许可；可能已发出的动作只读核验。恢复必须重新观察，不能重放点击。

## 4. 按依赖顺序实施

### M0：处理旧未决账本并建立可验证基线（先决条件）

- 在“执行记录”定位已授权的北京万联易达科技集团单次 CONTACT；只读核对现有证据。无法证明新消息则保留 `UNKNOWN`，由用户依据真实会话人工登记；系统不得自行裁定。
- 将浏览器当前账号、岗位 ID、招聘对象、会话 URL/页面可见身份、己方消息 `data-mid` 集合、消息送达状态封装为只读基线。仅保存关联所需最小数据和哈希，不存聊天全文。
- 为证据建立有效期和页面版本；在动作前发现账号/会话/岗位绑定不确定时停止，不能先点再补基线。

**验收**：旧未决动作仍可审计且未发生再次点击；在没有点击的条件下，可解释某条消息属于哪个会话、基线覆盖了哪些消息，无法绑定时明确报错。

**2026-10-01 进度**：指定搜索入口、真实只读小批次和聊天名片/消息候选基线已实现并现场核对；名片指纹不是平台会话 ID，旧 `UNKNOWN` 未结案，岗位与会话绑定仍缺失。M0 尚未整体通过。

### M1：真实 BOSS 开聊闭环

- 实现跨职位页、消息页的任务协调器，处理同标签跳转、新标签/弹窗和服务工作线程重启；以 `command_id + attempt_id + control_epoch` 关联一次动作，不靠弹窗是否打开判断成功。
- 先确认“立即沟通”是否自动发送平台已有招呼或只打开会话。若只打开会话且必须输入新文案，提供一次性固定招呼配置与任务授权；未配置时停在 `CHAT_OPENED`，不自行编造文本。
- 为 BOSS 单独实现消息增量证据提取器：点击前集合与点击后集合比较，要求新增己方消息、状态和招聘对象匹配。若 BOSS 没有足够稳定的招聘对象/岗位关联，标记 `BLOCKED` 并保留人工接管，不猜测。
- 在服务端和扩展分别配置 `CONTACT` 能力门禁。先在明确授权的受控岗位验证，再只解锁该账号、适配器版本和 CONTACT 能力；名单、过期和页面版本变化导致降级。默认仍关闭。

**验收**：至少覆盖新消息、旧消息、错误会话、页面跳转失败、超时、重复点击许可、重启后重连和用户接管；真实受控样本能证明本次新增消息，或明确 `UNKNOWN/BLOCKED`，且外部点击次数不超过授权次数。此阶段只可称“自动沟通”。

### M2：站内简历发送闭环

- 只读识别当前账号已有简历的可选择对象、类型、名称或平台稳定标识与版本；多份简历且无明确默认项时只进行一次绑定选择。不要上传新简历或随意挑第一份。
- 识别“发简历”可用、需双方回复、不可用及限制提示。对 `WAITING_PEER` 只保留待处理队列，下一次用户启动/恢复且条件已满足时重新检查；首版不假设长期后台监控。
- 按真实页面实现必要的简历选择与原生确认。每个可能产生外部效果的步骤记录意图和状态；新附件证据需绑定正确会话与简历。平台若只显示无身份的“已发送”，不能据此证明具体简历已投。
- `RESUME_SEND` 与 `CONTACT` 分别登记能力；开聊成功绝不自动解锁简历能力。

**验收**：本地模拟覆盖可发、等待回复、无入口、多份简历、错误简历、历史附件、超时及重复发送；真实受控样本至少有明确的可用/等待分支证据。只有在用户启动的受控真实样本取得本次新增且可关联附件的证据，才开放此账号的自动发送简历。

### M3：连续处理与可恢复任务

- 在聊天返回列表后恢复原北京推荐入口和列表锚点；不能依赖固定坐标或盲用浏览器后退。导航后重新核对右详情，候选队列与已处理 ID 持久化。
- 按账号串行执行；预算按实际处理流程计，已联系、待回复、失败和未知分开统计。用户暂停/恢复、浏览器休眠、扩展更新和服务重启后继续时，先核对账本，再读取页面。
- 同招聘人多岗位及共享会话按岗位、会话、附件三个层级分别去重：不能把同公司全部跳过，也不能给同一会话重复发同一附件并算多个新投递。

**验收**：至少两页列表、聊天往返、重复卡片、同招聘人多岗位、暂停/重启/断线各有回归用例；真实只读循环可稳定回到正确岗位，授权内小批次不发生错位或重复外部动作。

### M4：交付质量与扩大样本

- 扩展弹窗直接展示当前页/账号、两项能力状态、可开始原因、当前岗位、各结果计数、`WAITING_PEER` 和 `UNKNOWN` 的下一步；本地工作台承接详细证据与人工结案。避免所有按钮灰掉却无可执行解释。
- 模型只处理规则无法判定的岗位或未见过的页面状态：使用最小化文本、固定输出枚举、原文证据编号、超时和费用预算；失败回到 `NEEDS_REVIEW`。未经测试不把 Jev 放在关键发送链路。
- 补数据库迁移、日志脱敏、证据清理入口、扩展权限审查、账号切换/页面更新检测。关键 DOM 变化使相关能力自动退回 `UNVERIFIED`，不靠模型强行点击。

**验收**：`uv run pytest -q`、`uv run ruff check backend scripts/setup.py`、`npm test`、`npm run build` 和 `npm run test:e2e` 通过；另有真实 BOSS 验收报告，分别列 CONTACT 与 RESUME_SEND 的授权样本数、成功/失败/未知/接管、页面版本和证据。fixture 结果单列，不能合并为真实发送通过。

## 5. 放行标准和风险处置

| 放行级别 | 用户可做什么 | 必须满足的门槛 |
| --- | --- | --- |
| G0 只读 | 扫描与判断北京 AI 产品岗位 | 当前已具备；页面/账号失效时暂停 |
| G1 自动沟通 | 明确任务范围内自动点击“立即沟通” | M0 无账号级未决动作；M1 真实新增消息证据和跨页恢复通过；仅 CONTACT 能力 VERIFIED |
| G2 自动发送简历 | 已开聊且入口可用时自动发绑定简历 | G1、M2 附件身份及新增发送证据通过；RESUME_SEND 单独 VERIFIED |
| G3 连续批次 | 在预算内循环，等待回复的岗位可在后续任务继续 | M3 回到列表和重复保护通过；至少 G1 已验证。若未达到 G2，只能连续自动沟通，不宣称连续简历投递 |

关键风险是平台不能稳定暴露会话与岗位的绑定、附件身份或新消息回执。遇到这些情况，当前能力标记 `UNVERIFIED/BLOCKED`，岗位保留 `UNKNOWN/WAITING_PEER` 并交给用户，不使用 OCR 猜测、模拟接口、验证码绕过或高频重试替代证据。页面改版、账号切换、请求超时和休眠按同一规则处理。平台允许开聊但简历需招聘方先回复时，产品最多承诺自动沟通和后续条件满足时继续发送，不能承诺每个岗位立即完成简历投递。

## 6. 下一步开发入口

优先做 M0 与 M1 的只读会话绑定、动作前消息基线及增量证据提取器，再做跨页协调。完成本地负向用例后，在旧 `UNKNOWN` 结案且用户启动具体受控验证任务的前提下取得新的真实开聊样本；随后按 M2 处理附件。不要为了让扩展按钮立即变亮而删除 BOSS 的服务端发送门禁。
